# HOW-IT-WORKS — как это работает в движении

> Обновлено: 2026-08-15. Здесь **что происходит на самом деле**, шаг за шагом, и грабли
> библиотек. Структура — в [ARCHITECTURE](ARCHITECTURE.md), решения — в чертеже
> [STAGE-1-TELEGRAM](STAGE-1-TELEGRAM.md).

## Одно сообщение от начала до конца

Клиент пишет на аккаунт салона: **«здравствуйте, сколько стоит массаж спины?»**

### 1. Telegram отдаёт событие · `tg.py`

Наша программа вошла в аккаунт как ещё одно устройство. Событие приходит с фильтрами
telethon: `chats=` — белый список, `incoming=True` — только входящие,
`func=lambda e: e.is_private` — только личные чаты.

Событие превращается в простой объект `Входящее`: id чата, текст, дата (tz-aware UTC),
личный ли чат, исходящее ли, есть ли вложение, автор.

### 2. Читаем историю чата · `tg.py`

```python
get_messages(чат_id, limit=20, reverse=True)
```

⚠️ **`reverse=True` обязателен.** По умолчанию telethon отдаёт «from newest to oldest» —
модель увидела бы разговор задом наперёд.

Своей БД нет: Telegram и есть хранилище переписки. Одно чтение на пачку, а не на
сообщение — у `GetHistory` лимит около 10 запросов за 30 секунд.

### 3. Фильтры приёма · `guards.Приём`

Четыре проверки, любая отклоняет:

| Проверка | Зачем |
|---|---|
| исходящее? | иначе бот отвечает сам себе — петля |
| не личный чат? | в группах не отвечаем |
| дата раньше запуска процесса? | иначе первый запуск ответит на весь непрочитанный backlog |
| чат не в белом списке? | по умолчанию молчим |

Наивная дата (без таймзоны) отклоняется отдельно: сравнивать её с tz-aware — `TypeError`.

Проверки **дублируют** фильтры telethon намеренно: ошибка в фильтре молча открыла бы
доступ всем.

### 4. Группировка · `app.py`

Клиент печатает не мгновенно: «привет» / «сколько стоит» / «массаж спины» — три сообщения.

Сообщение кладётся в пачку по чату, таймер на 2.5 секунды тишины перезапускается. Когда
тишина настала — обрабатываем всю пачку одним запросом к модели.

⚠️ Корректность держится не на отмене таймера, а на том, что `обработать()` **забирает**
пачку через `pop`: повторный вызов уже ничего не находит. Отмена таймера — оптимизация.
Это выяснилось мутационной проверкой: ломали отмену — тесты оставались зелёными.

### 5. Нетекстовое

Голосовые в салонных чатах — норма, текста в них нет. У служебных сообщений текст вообще
`None`, не пустая строка. Проверяем `if not (текст or "").strip()` и отвечаем шаблоном:
«голосовые пока не разбираю, напишите текстом». Не падаем и не молчим.

### 6. Заслон до модели · `guards.медицинский_триггер`

Текст проверяется по списку из **56 корней**: боль, травма, операция, беременность,
противопоказания, диагнозы. Ищутся **от начала слова**, а не подстрокой — иначе
«больше» ловилось бы как «боль», а «кооперация» как «операц». **Сработал — модель не вызывается вообще.** Клиенту уходит
шаблон про администратора.

Это заслон, а не пометка: не «в логе появилась запись», а автоответ физически не
формируется.

Отдельно фильтр спама — **18 корней**, там просто молчим.

### 7. Сборка промпта · `prompt.py`

В системный промпт идёт: правила поведения, салон и адрес, все услуги с ценами и
длительностями, абонементы, мастера с полом и сменами, правила записи и **свободные окна
на три дня вперёд**.

Свободные окна считаются на месте: смена мастера минус занятые интервалы, шагом 30 минут,
услуга должна влезать целиком.

⚠️ В промпт попадает **только текущий чат**. Переписки других клиентов туда не идут:
согласие на ИИ-обработку не переносится между чатами.

### 8. Модель · `llm.py`

```python
reasoning_format="hidden"    # иначе рассуждения склеятся с текстом ответа
reasoning_effort="low"       # для вопросов о ценах глубина не нужна
response_format=json_schema  # + strict: форма гарантируется схемой
max_completion_tokens=700    # чтобы не приходила простыня
```

⚠️ **`reasoning_format="hidden"` — не оптимизация, а защита.** У `gpt-oss` в режиме `raw`
рассуждения приписываются прямо в `message.content`, **без тегов** — клиент получил бы
цепочку мыслей, и отфильтровать её было бы нечем.

Модель возвращает структуру:

```json
{ "reply": "Массаж спины 60 минут — 120 ₾. Сегодня свободно в 13:00 и 16:30.",
  "needs_human": false,
  "reason": "",
  "booking": null }
```

Если провайдер не ответил (429, сеть, ответ не по схеме) — **клиенту не отправляется
ничего**. Мусор хуже молчания. Пишем в лог.

### 9. Sender — единственный выход · `sender.py`

**Девять** проверок по порядку. Любая отклоняет:

| # | Проверка | Что делает при срабатывании |
|---|---|---|
| 1 | kill switch (файл `STOP`) | молчим |
| 2 | чат в белом списке | молчим |
| 3 | лимит ответов | молчим |
| 4 | администратор ответил раньше | молчим |
| 5 | `needs_human` от модели | шаблон администратору вместо текста модели |
| 6 | **текст ответа не пустой** | молчим: пустое сообщение Telegram и так не примет, а в лог попадёт причина |
| 7 | **все числа-цены есть в прайсе** | шаблон администратору |
| 8 | **всё названное время есть в окнах названного дня** | шаблон администратору |
| 9 | **обязывающие слова есть в правилах салона** | шаблон администратору |

Проверки 7, 8 и 9 — заслон от выдумки. Модель может ошибиться; отправка — нет.

⚠️ **Проверка 8 знает про день.** Она сверяет не с плоским множеством времён, а с окнами,
разложенными **по дням**, плюс часами работы (их можно называть про любой день).

На живых данных салона: 18:00–20:30 свободны **завтра** и невозможны **сегодня** — сегодня
смена кончается в 19:00. Плоское множество их содержало, поэтому «свободно **сегодня** в
20:30» проходило молча. Теперь заслон определяет день по метке в тексте:

| В тексте | Как трактуем |
|---|---|
| одна метка («сегодня» / «завтра» / «14.08») | относится ко всем временам — работает и «в 20:00 **завтра**» |
| несколько меток | у каждого времени ближайшая **слева** |
| меток нет | сверяем с **сегодня** — двусмысленный ответ лучше отдать человеку |

Отдельно от этого «записываемые» = только настоящие окна, без часов работы. По ним `Booker`
решает, можно ли записать: 21:00 назвать можно, записать на закрытие — нет.

⚠️ **Проверка 9 — самая новая и самая нужная.** Модель дважды приписала салону денежное
условие, которого в правилах нет: «будет удержана часть стоимости», «позже возврата не
будет». Ни цены, ни времени в этих фразах нет — проверки 7 и 8 к ним слепы. Приём: **словарь
обязательств задают сами правила из `price.yaml`**. Корень (`возврат`, `удерж`, `штраф`,
`скидк`, `гарантиру`…), которого нет в тексте правил, произносить нельзя. Дописали условие в
прайс — бот сразу вправе его называть, кода менять не надо.

При отклонении по 5–9 клиент **не остаётся без ответа**: уходит фиксированный шаблон
«передала ваш вопрос администратору». Он не сгенерирован моделью, поэтому выдумать в нём
нечего.

### 10. Если модель предложила записать · `booker.py`

Когда модель вернёт `booking`, `Booker` проверит три вещи:

| Заслон | Что отсекает |
|---|---|
| время **предложено нами раньше** или **названо самим клиентом** | запись на выдуманное время |
| свободно **в момент записи** | клиент подтвердил через 5 минут, за которые окно заняли |
| нет дубля: **пересечение интервалов** в один день у одного чата, **без мастера** | клиент дважды сказал «да» — и попытку обойти заслон сменой мастера |

⚠️ **Мастера в ключе дубля нет намеренно.** Раньше ключом было
(чат, дата, время, **мастер**) — и имитация обошла заслон в два хода: «запишите на
14:00» дало запись к одному мастеру, тот же запрос ещё раз — к другому. Формально не
дубль, фактически человек в двух креслах. Сравниваются не начала, а **интервалы**:
14:00–15:00 и 14:30–15:00 тоже несовместимы, хотя начала разные.

Прошло — запись дописывается в `data/bookings.yaml`, окно исчезает из свободных.

#### ⚠️ Порядок двух шагов здесь несущий

```
1. время, названное КЛИЕНТОМ в его сообщении  → в «предлагали» (до вызова модели)
2. попытка записи                              → Booker
3. время, названное НАМИ в ответе               → в «предлагали» (после записи)
```

Шаг 3 идёт **после** шага 2, и это не стиль. Живой диалог 2026-08-13: было наоборот,
клиент спросил «сколько стоит массаж спины?», модель ответила «предлагаю 13:00» — и в том
же ходу создала запись. Ответ **сам себе выдавал разрешение**, а шаг «предложили →
подтвердили» обходился целиком.

Шаг 1 — решение Георгия того же дня: клиент назвал свободное время сам → записываем сразу,
админа не звать. Пересечение со свободными окнами обязательно, иначе «запишите на 23:00»
стало бы записью.

### 11. Напоминания · `reminders.py` + цикл в `main.py`

Единственное, что уходит клиенту **первым**. Раз в минуту цикл смотрит записи и решает, что
пора отправить.

| Правило | Зачем |
|---|---|
| срок прошёл, визит не начался → пора | иначе после суточного простоя ушла бы рассылка о вчерашних визитах |
| созрели оба → уходит только ближайшее к визиту | два сообщения подряд выглядят как сбой |
| визит начался → все сроки гасятся молча | напоминать нечего |
| отметка `напомнили` лежит **в `bookings.yaml`** | флаг в памяти процесса не гарантия: упал, поднялся — напомнил второй раз |
| отказ отправки (`STOP`, белый список) **не гасит** | сняли `STOP` — уйдёт на следующем тике |
| текст фиксированный, **модель не участвует** | проверить сообщение, уходящее первым, перед отправкой некому |
| сбой тика перехватывается и логируется | задача создана через `create_task`: без перехвата рассылка умерла бы **навсегда и молча** |

Идёт через `Sender`, поэтому подчиняется тем же `STOP`, белому списку и лимиту. Выключатель:
`REMINDERS=off` в `.env` — тогда и промпт про напоминания не обещает.

## Отложенный ответ: клиент пишет через сутки

Контекст берётся не из памяти процесса, а из самого Telegram: последние 20
сообщений чата на каждую пачку. Поэтому разговор не «истекает» — ни через час,
ни через неделю, ни после перезапуска. Но три места всё равно ломались, и все
три закрыты 2026-08-15.

| Было | Стало |
|---|---|
| «да, давайте» на следующий день → **«записать не получилось»**: список предложенных времён жил в памяти процесса | предложенное **восстанавливается из наших же прошлых сообщений** в истории, пересечённое с записываемыми окнами. Своего состояния не добавилось |
| вчерашнее «свободно **завтра** в 13:00» модель читала как «послезавтра»: у сообщений истории не было даты | сообщения **не из сегодня датируются**: `(12.08) Свободно завтра в 13:00`, и промпт объясняет, что относительные слова внутри относятся к той дате |
| клиент написал ночью, процесс подняли утром → **ответа не будет никогда** | **добор при старте**: чаты, где последнее слово за клиентом, за последние 12 часов. `CATCHUP_HOURS=0` выключает |

Три границы добора, и каждая нужна:

1. **последнее слово за клиентом** — значит мы точно ещё не отвечали. Счётчик
   непрочитанных для этого не годится: мы не помечаем сообщения прочитанными, и
   он остаётся большим после нашего же ответа (проверено живьём — 35
   непрочитанных в отвеченном чате);
2. **не старше 12 часов** — отвечать «чем помочь» через сутки хуже, чем молчать;
3. **белый список** — его проверяет сам `Приём`, добор его не обходит.

⚠️ Обходится ровно **одна** проверка — отсечка «сообщение старше запуска», — и
обходится явным флагом `Входящее.догоняем`, а не сдвигом времени старта назад.
Сдвиг заставил бы отвечать заново на то, что мы **уже** ответили до перезапуска.

## Окно администратора · `aiconic/inbox/` (этап 2)

Включается `INBOX=on` в `.env`. По умолчанию выключено — этап 1 работает как раньше.

1. **Бот передал разговор человеку** — при `needs_human`, любом заслоне выхода, на
   медицинском триггере или когда запись не создалась. В `data/handovers.yaml`
   появляется метка: чат, **код** причины, время.
2. **Бот в этом чате замолкает.** Пока метка висит, модель не вызывается вовсе:
   иначе поверх слов администратора уйдёт ответ, который про них не знает.
3. **Администратор открывает страницу** с телефона: лента, сверху те, где ждут
   ответа, красным и с расшифровкой причины («вопрос о здоровье», «торг или скидка»).
4. **Заходит в разговор:** переписка **живьём из Telegram** плюс карточка — визиты
   из `bookings.yaml` и отметка причины. Слов клиента в карточке нет.
5. **Отвечает.** Текст уходит через `Sender.отправить_от_админа`: белый список
   проверяется, заслоны от выдумки модели — нет. Метка снимается, бот снова в работе.

Страница опрашивает ленту раз в 5 секунд, сервер кэширует её на 4 — у Telegram лимит
около 10 запросов истории за 30 секунд, и лента собирается **одним** вызовом
`get_dialogs()`. При возврате на вкладку обновление происходит сразу: телефон
засыпает и таймеры замирают.

## Лог: чем доказываем результат

Всё пишется в `logs/dialogs.jsonl`, по строке на событие: запрос к модели целиком
(системный промпт + сообщения), ответ модели целиком, решение `Sender` с причиной,
пропуски с причиной.

Без этого лога этап не даёт доказательств: качество ответов оценивается чтением, а не
ощущением.

## Запуск

```bash
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
copy .env.example .env          # заполнить
.venv\Scripts\python.exe login.py   # разово, по QR: печатает строку сессии
.venv\Scripts\python.exe main.py
```

⚠️ **Вход только по QR.** Код в приложение сторонним клиентам Telegram доставляет
ненадёжно, а SMS не отдаёт вообще: «only the official applications can receive a
login/signup code via SMS/call». Живой случай 2026-08-13 — код не пришёл никуда. QR от
доставки кода не зависит: подтверждает уже живая сессия на телефоне.

**Первый запуск — с пустым `TG_WHITELIST`.** Это режим наблюдения: процесс логирует id
всех, кто написал, и **никому не отвечает**. Возьмите нужный id из лога, впишите в
`TG_WHITELIST`, перезапустите.

⚠️ **`user_id`, который печатает `login.py`, в белый список НЕ годится** — это id аккаунта
салона. В список идёт id того, **кто пишет** салону, и его даёт только режим наблюдения.

Мгновенно замолчать: создать файл `STOP` рядом с `main.py`.

## Проверка

```bash
.venv\Scripts\python.exe -m pytest
.venv\Scripts\python.exe tools/mutants.py
```

Первое — тесты. Второе — **мутационная проверка**: ломает каждый заслон по очереди и
требует, чтобы защищающий тест покраснел. Зелёный тест не стоит ничего, пока не доказано,
что он умеет отвергать.

⚠️ **Добавили заслон — добавьте мутацию в `tools/mutants.py`.** Заслон без мутации не
считается проверенным.

Актуальные цифры прогонов — в [STATUS](STATUS.md).

## Грабли библиотек — коротко

| Грабля | Как обойдена |
|---|---|
| `import cerebras_cloud_sdk` **не существует** | `from cerebras.cloud.sdk import Cerebras` |
| `get_messages` отдаёт от новых к старым | `reverse=True` |
| `message.date` tz-aware, `datetime.now()` наивный | везде `datetime.now(timezone.utc)` |
| `text` бывает `None`, не только `""` | `(текст or "").strip()` |
| `gpt-oss` в `raw` склеивает рассуждения с ответом | `reasoning_format="hidden"` |
| `GetHistory` лимитирован ~10 запросов/30 с | одно чтение на пачку |
| `FloodWaitError` короче 60 с telethon отсиживает сам | перехватываем только длинные |
| `catch_up` по умолчанию `False`, но у него история багов | не полагаемся: своя отсечка по дате |
| **SMS с кодом входа сторонним клиентам Telegram не отдаёт** | вход по QR (`client.qr_login`) |
| **`force_sms=True` в Telethon 1.44 не работает** | «deprecated and no longer works» — флаг молча сбрасывается |
| **`create_task` глотает исключения** | цикл напоминаний перехватывает `Exception` сам, иначе умирает молча |
| **год в дате читался как цена** | `14.08.2026` → «цена 2026»; даты вырезаются до сверки цен |
